## 3. Gap list (concrete visual deltas)

1. **Layout: equal SimpleGrid → fixed 2-col `minmax(0,1fr) 360px`.** `CashierScreen.tsx` uses `SimpleGrid cols={{base:1,lg:2}}`; design wants left flex + fixed **360px** right panel with `gap:16px`. The current LEFT/RIGHT split also differs: design LEFT = "Joriy chek" (cart+search+pills), RIGHT = payment card + daily summary; current RIGHT = daily summary + transactions table (payment controls live inside the LEFT `PosPanel`). Reorganizing LEFT/RIGHT semantics risks functional churn — re-skin in place (token+radius+spacing), keep the payment controls where they are unless the task is scoped to move them.
2. **Card chrome.** Current `Card/Paper withBorder radius="md"` → design `radius:16px`, `box-shadow:var(--shadow-sm)`, `border:1px solid var(--border)`, `background:var(--surface)`. Header rows want `padding:16px 18px; border-bottom:1px solid var(--border)`.
3. **Service add UX: `Select` dropdown → quick-add category pills.** Design renders 7 catalog pills (`height:31px; radius:99px`, green `+`, hover teal-soft). Current uses a single searchable `Select`. This is a real interaction change — keep `addService()` logic, restyle the trigger surface (search input row + pill row) without altering cart-add behavior.
4. **Discount control: so'm `NumberInput` → percent pills `[0 5 10 15]`.** **DELTA WITH FUNCTIONAL IMPACT — money invariant.** Design discount is **percent** (`discAmt = round(cartSub*disc/100)`); current discount is an **absolute so'm amount** passed straight into `computeNetTotal`/`buildCreatePayload`. Re-skinning the visual to pills is fine **only** if it still emits the same absolute-so'm value the math expects — i.e. pills must compute `percent → so'm` before calling the mappers, leaving `computeNetTotal`/`buildCreatePayload` untouched. If percent semantics can't be reconciled without touching math, keep the so'm input and only restyle it. Flag for the impl owner; **do not change `cashier.mappers.ts`.**
5. **Payment method: 4-option `Select` → 3-button toggle.** Design = `Naqd / Karta / Aralash` 54px toggle buttons (active = primary-soft + 1.5px primary border). Current = `Select` with cash/card/transfer/**other**. Map the toggle to the existing `PaymentMethod` union (`cash`/`card`/`transfer`); decide where `other` goes (likely drop from the toggle but keep the type — confirm with i18n keys `cashier.method.*`). Keep `paymentMethod` state + payload wiring.
6. **Cart row styling.** Design = 3-col grid (name+cat / mono price / `×`), read-only-looking. Current = editable qty/price `NumberInput`s + `IconTrash`. Keep editing functional; restyle to grid + mono price + token-based `×` remove (hover `danger-soft`). Show service **category** as the sub-line (data available from `Service`).
7. **Accept button.** Current teal `Button` with `IconCash` inline in a `Group` → design full-width 46px primary button "To'lovni qabul qilish" with NoOp caption beneath. Restyle; **no receipt modal exists** — adding a print-ready receipt (`chekOpen` equivalent) is net-new (see Task D).
8. **Daily summary "Bugungi kassa".** Current `Table` of breakdown → design compact "Jami tushum" + two `surface-2` stat boxes. Restyle within `DailySummaryCard.tsx` using `formatCurrency`/`formatNumber`.
9. **Services screen.** Token/radius sweep for `ServicesScreen`/`ServicesTable`/`ServiceFormModal`/pricing tabs to match DS card chrome (`radius:16px`, `shadow-sm`, header padding). Lower visual priority; keep grouping + CRUD behavior.
10. **Receipt modal is print-ready & theme-independent.** If built, fonts (`'JetBrains Mono'`, `'Hanken Grotesk'`) + light palette (`#fff/#192420/#5a6a64`) are hardcoded by design (paper). Do **not** wire it to dark-mode tokens.

## 5. Risks / notes

- **BILLING INVARIANT — never change money logic.** `cashier.mappers.ts` (`computeNetTotal`, `buildCreatePayload`, `buildAllocationPayload`, `findActivePrice`, VM mappers) is locked. The **discount unit mismatch** is the single biggest trap: design uses **percent (0–15)**, code uses **absolute so'm**. Re-skinning to percent pills is allowed only if the pill emits the correct absolute-so'm discount before the mappers run; otherwise keep the so'm input and just restyle. Characterization tests exist (`cashier.mappers.test.ts`, `PlanBillingPanel.test.tsx`, `PosPanel.test.tsx`, `CashierScreen.test.tsx`) — they must stay green. This is a **re-skin, not a re-architecture (Qaror #33).**
- **`formatCurrency` / `formatNumber` (CLI-166).** All money strings go through `lib/format.ts`. Never inline `Intl.NumberFormat` or hardcode `so'm`/`сум`. The receipt modal's literal `so'm` in the design footer must still come from `t('common.currency')`. Count columns ("… xizmat") use `formatNumber`.
- **Consent modal ownership — OPEN DECISION (owner-gated, do not resolve unilaterally).** The DS6 milestone title and the design-source paragraph both **name the consent PDF modal** as in-scope. But there is a genuine **contradiction in the prompt**: the task framing says "note which touch services vs cashier" (leaving no room for a clinical-folder task), while the title says consent is DS6. Surfacing this is the brief's job; the owner picks.
  - **Current state:** the only consent UI today is `features/clinical/components/consent/ConsentTab.tsx` — a **sign/template flow**. The design's `consentOpen` is a **print-ready formal-document view** — likely a **different, net-new** modal (mirror how the receipt is net-new), not a re-skin of `ConsentTab`. This should be **verified** against `ConsentTab.tsx` before scheduling.
  - **Option A (DS6 owns it):** add Task G (cross-folder — touches `features/clinical`, breaks the cashier+services file-disjointness this brief assumes). Consistent with treating the receipt as a net-new build (Task D).
  - **Option B (defer to the clinical milestone):** consent lives where its sign/template flow already lives; DS6 ships receipt only. **Caveat:** "clinical milestone" is unverified — CLAUDE.md only confirms DS1=Dashboard; do not assume a DS7=Clinical mapping without checking the roadmap.
  - **Recommendation:** owner picks A vs B after verifying whether the print-document modal is net-new vs a `ConsentTab` re-skin. The brief does **not** drop the deliverable.
- **Print-ready modals are theme-independent.** Receipt (and consent) modals hardcode `'JetBrains Mono'` + `'Hanken Grotesk'` and a fixed light palette (`#fff`, `#192420`, `#5a6a64`, dark header `#10201c`) — they are paper documents. Do **not** wire them to `tokens.css` dark-mode vars. The interactive POS chrome **is** token-driven and must work in both themes.
- **Dark-mode contrast gate (DS0 lesson — CLI-80/255 regression).** Every token remap must be re-checked in dark mode for WCAG AA. Watch the active payment toggle (`--primary-soft` bg + `--primary` text) and discount pills (`--primary` bg + `--on-primary` text) in dark — confirm `--on-primary` / `--text-on-*` tokens resolve and contrast holds. Bake the contrast check into Task F.
- **Category pills vs Select is an interaction change, not pure re-skin.** Replacing the service `Select` with quick-add pills changes how a clinician adds services. Keep `addService()` semantics (dedupe → qty++, async price autofill via `fetchServicePrices`/`findActivePrice`) intact; only the trigger surface changes.
- **No new API / permissions.** All data already available via existing `cashier.api.ts` hooks; `cashier.view` / `cashier.create_transaction` / `cashier.refund` gating unchanged.

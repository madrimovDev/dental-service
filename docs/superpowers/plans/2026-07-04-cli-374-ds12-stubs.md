# CLI-374 ds12 Data-Gap Stubs Coming-Soon Treatment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resolve the two ds12 stubs so neither is indistinguishable from — or, worse, contradicts — a real result: (1) `WaitlistCard` (always-empty, ignores its `appts` prop) gets the project's existing "coming soon" label (`t('shell.coming_soon')`, precedent: `apps/web/src/shell/Sidebar.tsx:217/221`, also reused by CLI-372) via the `@dental/ui` `Tag` primitive; (2) `DayStatsCard`'s "Bo'sh slot" KPI tile (hardcoded `'—'`) is **removed entirely**, because `FreeSlotsCard` — rendered directly below it in the same `CalendarScreen.tsx` rail, under the identical `appointments.free_slots` label — already shows real, live free-slot data for users with `schedule.view`. Adding a "coming soon" Tag to the `DayStatsCard` tile instead would create a same-screen contradiction (one card claims "not built," the adjacent one proves otherwise) — worse than today's ambiguous `—`. No backend work, no new endpoints, no new i18n keys.

> ⚠️ **This plan implements the deviation flagged in the spec's warning box** (`docs/superpowers/specs/2026-07-04-cli-374-ds12-stubs-design.md`, right after §1): Task 2 removes a tile rather than adding a "coming soon" badge to it, which is neither of the ticket's two literal DoD options. Get sign-off on that spec section before running Task 2.

**Architecture:** Pure presentational change confined to two existing leaf components. `WaitlistCard.tsx` gets one `Tag` element added to its existing static "chrome" div (see spec §2.1/§4.1), reusing the `shell.coming_soon` i18n key (no duplicate key added, matching the CLI-372 precedent). `DayStatsCard.tsx` gets one entry removed from its `tiles` array (see spec §2.2/§4.2) — no new component, no prop changes needed for it. Full backend-data implementation (building a real waitlist backend, or re-wiring a free-slot KPI tile to the already-existing `useBranchAvailability` hook in some other context where `FreeSlotsCard` isn't already present) is explicitly deferred — see spec §5 Follow-up.

**Tech Stack:** React, Mantine v7, react-i18next, `@dental/ui` (`Tag` primitive), Vitest + Testing Library (`renderApp` from `apps/web/src/test-utils.tsx`)

## Global Constraints
- Scope is visual clarity/contradiction-removal only, not full feature implementation (see spec §4 for why: `DayStatsCard`'s free-slot data source exists via `useBranchAvailability`/`FreeSlotsCard` already rendered on the same screen — duplicating it into a KPI tile, with or without a badge, is out of this ticket's scope; `WaitlistCard`'s data source does not exist in the backend at all).
- No new i18n keys — reuse `shell.coming_soon` (uz: "Tez orada", ru: "Скоро") exactly as CLI-372 did.
- Do not remove or rename `data-testid`s that remain in use (`waitlist-empty`, `day-stat-total`, `day-stat-confirmed`, `day-stat-pending`) — existing tests depend on them. `day-stat-free` is intentionally removed as part of Task 2 (the tile it identified no longer exists).
- Do not touch `FreeSlotsCard.tsx` or `DayStatsCard.tsx`'s `total`/`confirmed`/`pending` tiles — those already show real, live data and are out of scope.

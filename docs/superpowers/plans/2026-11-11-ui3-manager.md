# UI-3 — Rahbar (M1–M6) + desktop zaxira/tiklash Implementation Plan

> **For agentic workers:** superpowers:executing-plans. Ijro: `docs/ORCHESTRATION-GUIDE.md` (§5.5 integratsiya, §6b vizual qabul). Steps `- [ ]`.

**Goal:** rahbarning 6 ta ekrani yangi dizaynda va desktop'da zaxira/tiklash funksiyasi.

**Architecture:** 4 lane: **A** M1 Rahbar bosh sahifasi → M2 Hisobotlar; **B** M3 Sozlamalar → M4 Xodimlar; **C** M5 Ombor → M6 Xarajat va ish haqi; **D** desktop zaxira/tiklash (API + Electron main + Sozlamalar bo'limi komponenti).

**Spec:** `docs/superpowers/specs/2026-11-11-ui-redesign-design.md` §2.3 (UI-M1…M6 qatori — MAJBURIY), §0/§1/§4; roadmap `docs/superpowers/specs/2026-11-11-completion-roadmap-design.md` §4.1 (zaxira/tiklash qarorlari). Kanvas: `{OwnerDashboard,Reports,Settings,Staff,Stock,Finance}.dc.html`.

## Global Constraints

- Zaxira (👤/🛠 roadmap §4.1): **faqat desktop**; papka Sozlamalar'da (default `D:\DentalBackup`, D: yo'q bo'lsa `C:\DentalBackup`; Linux dev'da `<dataDir>/backups`); har kuni **20:00** avtomatik + «Hozir zaxira olish»; tarkib `pg_dump -Fc` + uploads arxivi; **oxirgi 14 nusxa**; rahbar sahifasida holat, **>2 kun** zaxirasiz → ogohlantirish. **Tiklash UI orqali, faqat owner**, `CriticalActionDialog`da klinika nomini qo'lda yozish, tiklashdan oldin avtomatik zaxira, tiklash paytida klientlar «Texnik ish» ko'radi. Bulut (SaaS) rejimida zaxira bo'limi ko'rinmaydi.
- Zaxira kontrakti (lane A M1 shu bilan ishlaydi): `GET /api/backup/status` → `{ mode: 'desktop'|'cloud', folder: string|null, lastSuccessAt: string|null, lastError: string|null, files: { name, sizeBytes, createdAt }[] }` (`tenant_settings.view` yoki owner); cloud'da `{ mode:'cloud', ... null }`.
- Tiklash arxitekturasi: API `POST /api/backup/restore { file, confirmName }` (owner-only, `confirmName === tenant.name`, fayl zaxira papkasida bo'lishi shart — path traversal yo'q) → `<dataDir>/restore-request.json` yozadi va 202 qaytaradi; **Electron main** uni kuzatadi (`fs.watch` yoki 2 s polling) → API'ni to'xtatadi → `createPgTools().dump` (pre-restore) → `restore(file)` (P2 dagi mavjud funksiya — `pg_restore --list` tekshiruvi bilan) → uploads arxivini tiklaydi → API'ni qayta ishga tushiradi → natijani `restore-result.json`ga yozadi. Electron'siz (dev/cloud) endpoint 404.
- 20:00 jadvali **Electron main**da (API emas), `node-cron` YO'Q — oddiy `setTimeout` keyingi 20:00 gacha; API `POST /api/backup/run` ham `<dataDir>/backup-request.json` orqali main'ga topshiradi. Holat `<dataDir>/backup-state.json`.
- P-qarorlar: M4 — P5/P6/FU-08 allaqachon backend'da (bu bosqichda faqat UI: rol kartalari «qila oladi / qila olmaydi», ruxsat etilmagan rol `aria-disabled`, «Kutilmoqda», vaqtinchalik parol bir marta); M3 — P10 ish soati muharriri mavjud (UI-1/P10), readiness checklist yangi endpoint.
- Matnlar `t()` — namespace'lar: `ownerHome.*`, `reportsQ.*`, `settingsShell.*`, `staffCards.*`, `stockScreen.*`, `finance.*`, `backup.*`.
- Rol testi real permset (Owner, Tenant Admin, Branch Manager, Accountant), `@owner` emas — M2 branch scoping server tomonida (IR-06).
- Migratsiya: zarur bo'lsa faqat lane C — **0053** (masalan IR-01 boshlang'ich qoldiq ledger). Boshqa lane'lar migratsiya yaratmaydi.
- Windows-only xulq (D: papka, 20:00 jadval, Electron restore) — Linux'da unit + real-PG testi (`P2_PG_TEST` naqshi); holat 🟡, `windowsChecklist` hisobotda.
